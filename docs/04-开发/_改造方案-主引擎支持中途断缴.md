# 改造方案：主引擎支持中途断缴

> 2026-09-19 评估。针对 `pension-engine.js`（云函数版，105 KB）。
> 未动代码，本文为改造设计。行号以 `cloudfunctions/calculate/pension-engine.js` 为准。

---

## 一、现状诊断

### 1.1 主引擎完全不支持断缴

| 环节 | 位置 | 现状 |
|---|---|---|
| 年限 | `calcYears()` L1476–1480 | **纯减法**：`(end.year-start.year)*12 + (end.month-start.month)`，无任何扣减项 |
| 年限组装 | L1756–1759 | `totalYears = calcYears(actualStart, legalDate) + sightYears`，假设全程连续 |
| 个人账户 | `calcPersonalAccountPension()` L380–412 | **逐年循环**（第一年 / 中间年 / 最后一年），每年无条件存入，无跳过机制 |
| 平均缴费指数 | L1494 | `parseFloat(inputData.avgIndex)`，**标量输入**，引擎不逐年算指数 |

### 1.2 关键发现：两个引擎能力不对称

- **缴费指数计算器（`calc-index.js`）已经支持断缴**：D6 规则 31 省齐全——
  `gapZero: true`（京/津/陕/浙/云，断缴年计入分母记 0）、`gapFloor: 0.6`（黑龙江，记 0.6）、
  其余（如重庆）不计入分母。
- **养老金主引擎（`pension-engine.js`）一点都不支持。**

⇒ **断缴后的平均缴费指数算得出来，断缴后的养老金算不出来。** 这是改造的真正动机。

### 1.3 好消息：改造基础已具备

个账那段是**逐年循环**（L380–412），每年可独立判断；`calcYears` 是纯函数，加一个扣减参数即可。
**不需要重构，只需在既有结构上打洞。**

## 二、改造清单（六层）

### 第 1 层 · 输入层（新增）

新增参数 `breakPeriods`（断缴区间数组）：

```js
inputData.breakPeriods = [
  { start: { year: 2010, month: 7 }, end: { year: 2013, month: 6 } },  // 含首尾月
  { start: { year: 2018, month: 1 }, end: { year: 2018, month: 12 } },
]
```

`parseInput()`（L1487 起）内需做四项校验：

| 校验 | 处理 |
|---|---|
| 区间越界（早于参工 / 晚于退休） | 截断，不报错 |
| 区间重叠 | 合并后去重 |
| 起止倒置 | 自动交换 |
| 跨建账时间点（`account_start`） | **拆成两段**，分别归入视同期 / 实缴期（见第 2 层） |

**建议同时支持简化形态** `breakYears: [2010, 2011, 2012]`（整年断缴），覆盖"忘了哪个月"的多数场景。

### 第 2 层 · 年限层（核心）

`calcYears()` 增加可选扣减：

```js
function calcYears(start, end, breaks = []) {
  if (!start || !end) return 0
  let totalMonths = (end.year - start.year) * 12 + (end.month - start.month)
  for (const b of breaks) totalMonths -= overlapMonths(start, end, b)   // 新增
  return Math.max(0, totalMonths / 12)
}
```

L1756–1759 的组装处必须**把断缴拆到两个桶**：

- **落在建账前**（`work ~ sightCutoff`）的断缴 → 扣 `sightYears`
- **落在建账后**（`sightCutoff ~ legalDate`）的断缴 → 扣 `actualYears`，进而 `totalYears`

⚠️ **这里有一个必须先拍板的问题**（见第三节决策 B）：建账前"断缴"是否扣视同年。
视同年限本质是**连续工龄认定**，离职中断确实会断工龄，但各地认定口径差异极大，
默认建议**扣**（更符合实际），但要允许通过 `sightBreakDeduct: false` 关掉。

### 第 3 层 · 个账层（改动最小，收益最大）

`calcPersonalAccountPension()` 的逐年循环（L395–402）里加一句判断：

```js
for (let y = fYear + 1; y < retireDate.year; y++) {
  const paid = paidMonthsOfYear(y, breaks, accStart, retireDate)   // 新增：本年实缴月数
  if (paid <= 0) {
    // 断缴：不存入，但上年末余额照常计息
    totalAcc = totalAcc * (1 + getAccRate(y, config))
    continue
  }
  const annualPay = baseYear * avgIndex * 0.08 * paid              // 12 → paid
  totalAcc = totalAcc * (1 + accRate) + annualPay
}
```

**关键点：断缴年不存入，但已有余额继续按当年记账利率复利。** 这一条是断缴影响里最反直觉、
也最值得写进文章的——断缴不是"清零"，是"停止注入但继续滚"。

第一年（L383–391）和最后一年（L405–412）同样要按 `paid` 折算。

### 第 4 层 · 指数层（最大分歧点，见决策 A）

平均缴费指数目前是标量输入。**断缴年到底进不进分母，31 省三种规则**：

| 规则 | 省份 | 断缴年处理 |
|---|---|---|
| `gapZero` | 京 / 津 / 陕 / 浙 / 云 | 计入分母，指数记 **0** |
| `gapFloor` | 黑龙江 | 计入分母，指数记 **0.6** |
| 默认（含重庆） | 其余 | **不计入分母** |

⇒ 主引擎不能自己拍，必须由 `calc-index.js` 按省规则算好再传入。

### 第 5 层 · 输出层

`legal` 返回值增加断缴明细，供前端展示与文章配图：

```js
breakInfo: {
  totalBreakMonths, sightBreakYears, actualBreakYears,
  yearly: [{ year, paidMonths, isBreak, indexUsed }],   // 逐年清单
  note: '断缴年已按本省规则计入/不计入指数分母'
}
```

### 第 6 层 · 副本同步（红线）

**`pension-engine.js` 全仓库 8 份**（2026-09-12 血泪教训：首轮只同步 3 份、漏掉线上那份）。
改完必须按函数特征找全：

```bash
grep -rl "calcYears\|calcPersonalAccountPension" --include=*.js . | grep -v node_modules
```

| 文件 | 说明 |
|---|---|
| `engine.js`（根） | **★ 线上** |
| `engine/pension-engine.js` | 源 |
| `cloudfunctions/calculate/pension-engine.js` | 云函数 |
| `web/engine.js` | 构建产物 |
| `docs/js/pension-engine.js` 等 3 份 | 旧代际，**只能精准 patch，不能整体覆盖** |

## 三、三个必须先拍板的设计决策

### 决策 A · 指数谁算？

| | 方案甲（推荐） | 方案乙 |
|---|---|---|
| 做法 | 主引擎只管年限 + 个账，**指数仍由 `calc-index.js` 算好传入** | 主引擎内嵌逐年指数数组，自己算加权平均 |
| 工作量 | 小（不动第 4 层） | 大（需把 D6 规则导入主引擎） |
| 优点 | 职责清晰；D6 规则已在 calcIndex 里跑通并验证过 | 一次调用出全部结果，小程序端体验好 |
| 风险 | 调用方要串两次引擎，口径易错 | 两套指数逻辑并存，日后必然不同步 |

**建议甲。** 除非产品要求"一次输入出全部结果"，否则不要让主引擎重算指数——
现在 `calc-index.js` 的 31 省 D6 是已验证资产，复制一份就是双份维护成本。

### 决策 B · 建账前的断缴，扣不扣视同年？

- **扣**（默认建议）：视同 = 连续工龄，离职中断就是断了，符合多数地区认定。
- **不扣**：部分地区的视同认定与事后是否连续缴费无关（如某段固定时期的国企工龄照认）。

⇒ 建议做成**可配置开关**（`sightBreakDeduct`，默认 `true`），并在 UI/文章中显式说明本省口径。

### 决策 C · 断缴后补缴怎么算？

现实里断缴有三种后续，引擎目前一种都不支持：

1. **事后追补**——灵活就业**不允许**（国发〔2014〕8 号等），单位原因断缴**可以**补
2. **延缴**——到退休年龄不满 15 年，继续缴至满 15 年
3. **一次性补缴**——2011-07 前参保、延缴 5 年后仍不足 15 年

⇒ 建议**一期只做"纯断缴"**（不补），把补缴留到二期。一期若混入补缴，参数模型会立刻复杂一倍
（补缴基数按哪年、是否收滞纳金、补缴年指数怎么算），且各省口径更乱。

## 四、工作量与风险

| 层 | 工作量 | 风险 |
|---|---|---|
| 第 1 层 输入 | 小 | 校验规则多，但都是纯逻辑 |
| 第 2 层 年限 | 中 | **跨建账点拆分**是唯一难点 |
| 第 3 层 个账 | **小**（循环已存在） | 低 |
| 第 4 层 指数（甲方案） | 无 | — |
| 第 5 层 输出 | 小 | 低 |
| 第 6 层 副本同步 | 中 | **高**——8 份，漏一份就是线上事故 |

**总体：中小改造，核心工作量在"跨建账点拆分"和"8 份副本同步"，不在算法本身。**

### 其他风险

1. **断缴 + 弹性退休 / 延迟退休叠加**：`legalDate` 由政策推导，断缴区间可能与之冲突（断缴晚于法定退休月），需校验。
2. **最低缴费年限判断（2030 起提到 20 年）**：断缴后 `meetMin` 的判断要跟着改，否则会误判"已满足"。
3. **医保断缴是另一套规则**（等待期 3~6 个月），**不要混进来**，本文只谈养老。
4. **回归基线**：`tests/test-engine.js` 现为 35/41（6 个既有失败与本次无关）。改造后必须先跑基线确认 35/41 不变，再看新增用例。

## 六、改造后能回答的问题（这才是价值）

现在引擎只能回答"22 岁一路缴到退休"。支持断缴后能回答：

- 断 1 年 / 3 年 / 5 年 / 10 年，月领各少多少？
- **早年断缴和晚年断缴，哪个亏更多？**（预期：早年断更亏——既少年限，又错过低基数时期的便宜缴费）
- 断缴年不存入但继续计息，实际损失比直觉小多少？
- 缴满 15 年就停 vs 断断续续缴 25 年，哪个划算？

⇒ 最后一条正好接上选题 E（缴满就停），也能补上现在只能靠"晚参保"代理的口径缺陷。
