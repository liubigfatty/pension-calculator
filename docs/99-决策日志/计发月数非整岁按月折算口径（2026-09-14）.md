# 决策：计发月数非整岁改为「按月线性折算」（2026-09-14 修正并落地）

> 触发：用户问「计发月数为什么还用插值呢？不是全局配置的对照表吗？」
> 结论：**恰恰相反——政策口径就是按月折算**，原实现（四舍五入到整岁查表）是 bug。
> 状态：**已修复、已部署、文章已同步**（提交 `60d3b13`）

## 一、政策口径（不是插值，是查表 + 折算）

延迟退休落地后，退休年龄普遍带零头（50 岁 4 个月、60 岁 3 个月）。人社部配套口径：

```
实际计发月数 = 上一整岁值 − (上一整岁值 − 下一整岁值) ÷ 12 × 超出月数
```

保留 1 位小数。实证：

| 来源 | 案例 |
|---|---|
| 深圳养老金核定单（真实单据） | 60 岁 4 月 → 计发月数 **136.7** |
| 官方《2025年1月后退休个人账户养老金计发月份表》 | 50 岁 6 月 = **192.5**、60 岁 3 月 = **137.3** |

验证：本项目 `docs/网页版/js/pension-engine-browser.js` 里的 `STANDARD_MONTHLY_PAYMENT_MONTHS`
（181 条，50 岁 0 月 ~ 65 岁 0 月，键为总月数）与上述公式**逐项吻合**——
**这张按月精细表本来就在库里，只是主引擎没用它。**

## 二、原实现的错误

```js
// 原 getRetireMonths
const roundKey = Math.round(ageExact) + '.0'   // 50.5 → 51.0 → 190
```

| 退休年龄 | 原实现 | 正确值 | 偏差 |
|---|---|---|---|
| 50 岁 4 个月 | 195 | **193.3** | +0.9% |
| 55 岁 3 个月 | 170 | **168.5** | +0.9% |
| 60 岁 3 个月 | 139 | **137.3** | +1.2% |

计发月数是除数，偏大 ⇒ **个人账户养老金被系统性低估约 1.3%**。
延迟退休后几乎人人非整岁退休，影响面覆盖全部新退休人群。

## 三、新实现（`engine/pension-engine.js`）

1. `totalM = round(ageExact × 12)` 归一化，避免十进制年的浮点误差
2. ① 精细表优先（总月数键 `"723"` / 岁月键 `"60.3"`）
   ② 整岁基准表（国发〔2005〕38 号）
   ③ 非整岁按月线性折算，保留 1 位小数
3. 边界：低于 40 周岁按 40、高于 70 周岁按 70（沪人社规〔2021〕27 号）
4. 无 `DEFAULT_MONTHLY_PAYMENT_MONTHS` 常量的浏览器 shim 副本内联兜底表

同步脚本：`scripts/_sync_retire_months.js`（7 份副本全覆盖）

## 五、附带沉淀：验算脚本 `--update` 模式

引擎口径一变，几十处快照期望值集体失效。新增 `scripts/_inject_update_mode.js`，
给验算脚本的 `ok()` 注入「用当前实际值回写源码」能力：

```bash
node scripts/_inject_update_mode.js          # 注入（幂等）
node scripts/_verify_lever.js --update       # 刷新期望值
node scripts/_verify_lever.js                # 正常校验
```

设计要点（踩过的坑）：
- 占位符用 `split().join()`，`String.replace` 只替换首次出现
- 模板字符串里的正则要双写反斜杠（`\\s`），否则被吞成 `s`
- 正则兼容 CRLF；脚本末尾 `process.exit()` 须改为 `if (!__UM) process.exit(...)`
- **循环内断言（同一行多次调用）自动跳过交人工**——否则只留第一次的值会改坏其余
- 精度自适应容差 `digits = min(8, max(2, ceil(-log10(tol))+1))`
